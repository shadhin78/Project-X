# Project X Local Database Layer & Storage Documentation

Project X implements a robust offline-first caching and storage architecture using a combination of **Dexie.js (IndexedDB)** and **HTML5 LocalStorage**. 

---

## 1. Storage Technologies & Locations

### IndexedDB (Primary Database)
- **Engine**: [Dexie.js](https://dexie.org/) (a lightweight, premium wrapper around native IndexedDB).
- **Database Name**: `ProjectXLocalDB`
- **Location**: Browser Sandbox directory. You can inspect it directly:
  1. Open Chrome/Edge/Firefox Developer Tools (press `F12` or `Ctrl + Shift + I`).
  2. Navigate to the **Application** tab (Chrome/Edge) or **Storage** tab (Firefox).
  3. Expand the **IndexedDB** tree list.
  4. Select **`ProjectXLocalDB`**.

### LocalStorage (Legacy / Fallback Backup)
- **Fallback Keys**:
  - `studyMasterBackup`: Stores a stringified JSON payload containing a snapshot of all application memory state.
  - `studyPlan_profileName`: Custom override for user name.
  - `studyPlan_profileEmail`: Custom override for user email.

## 2. Dexie.js Database Schema

The database contains seven tables initialized under version `2` of `ProjectXLocalDB`:

| Table Name | Schema Descriptor / Indexed Fields | Purpose |
| :--- | :--- | :--- |
| `tasks` | `id, date, type, studyDay` | Holds daily study tasks, holiday markings, and individual track assignments. |
| `timerLogs` | `++id, subject, duration, timestamp` | Records elapsed time tracking logs generated by the Timer page. |
| `scheduleBlocks` | `id, day, startTime, endTime, task, track, program, color, isDayStart` | Standard schedule routine allocation blocks (Routine Set 1). |
| `scheduleBlocks2` | `id, day, startTime, endTime, task, track, program, color, isDayStart` | Alternative schedule routine allocation blocks (Routine Set 2). |
| `scheduleGroups` | `id, name` | Schedule groups created for organizing track structures. |
| `appSettings` | `key, value` | Key-value store for app metadata, custom priorities, weekly targets, and syllabus configurations. |
| `syncQueue` | `++id, timestamp, status` | Queue tracking local changes waiting to sync back to Firestore. |

## 3. CRUD API (Window Interface)

All local database transactions are exposed under the global `window.localDBHelper` namespace:

### Tasks CRUD
- **Create / Update**: `await window.localDBHelper.createTask(taskObject)` or `await window.localDBHelper.updateTask(taskObject)`
- **Read**: `await window.localDBHelper.readTask(id)` (Single record) or `await window.localDBHelper.readAllTasks()` (Array of all tasks)
- **Delete**: `await window.localDBHelper.deleteTask(id)`

### Timer Logs CRUD
- **Create**: `await window.localDBHelper.createTimerLog(logObject)`
- **Read**: `await window.localDBHelper.readTimerLog(id)` or `await window.localDBHelper.readAllTimerLogs()`
- **Update**: `await window.localDBHelper.updateTimerLog(logObject)`
- **Delete**: `await window.localDBHelper.deleteTimerLog(id)`

### Routine 1 / 2 Blocks CRUD
- **Create**: `await window.localDBHelper.createScheduleBlock(block)` / `createScheduleBlock2(block)`
- **Read**: `await window.localDBHelper.readScheduleBlock(id)` / `readAllScheduleBlocks()` / `readAllScheduleBlocks2()`
- **Update**: `await window.localDBHelper.updateScheduleBlock(block)` / `updateScheduleBlock2(block)`
- **Delete**: `await window.localDBHelper.deleteScheduleBlock(id)` / `deleteScheduleBlock2(id)`

### Key-Value App Settings CRUD
- **Write**: `await window.localDBHelper.setSetting(key, value)`
- **Read**: `await window.localDBHelper.getSetting(key)`
- **Delete**: `await window.localDBHelper.deleteSetting(key)`

## 4. Offline Sync Queue Manager Service (`window.syncManager`)

To support reliable offline data collection and synchronization back to Firebase Firestore, a dedicated **Sync Manager Service** runs in the background.

### Sync Queue Item State Model
Each change object enqueued is tracked as a record in the `syncQueue` store with one of the following states:

1. **`pending`**: Change is enqueued and waiting to sync. If multiple edits are made while offline, the Sync Manager collapses duplicate operations by updating the single existing pending payload to minimize overhead.
2. **`syncing`**: Connection is active and the sync item is currently being transmitted to Firebase. This state locks the record to **prevent duplicate sync operations**.
3. **`synced`**: The item has successfully been written to the remote database.

### Core APIs
- `await window.syncManager.enqueue(payload)`: Debounces and stores changes in the `syncQueue` table and immediately triggers a process queue request.
- `await window.syncManager.processQueue()`: Validates network connectivity, locks and sequentially resolves pending queue items.
- `await window.syncManager.updateSyncStatusUI()`: Controls the visibility of the visual `#sync-status` icon indicator badge dynamically.
